Class Model

The class model of EDUTASK outlines the structure of the system by defining its classes, their attributes, and the relationships that hold between them. It shows how a task moves from the Director or Staff who creates it, through the teacher who acknowledges and works on it, to the evidence that is submitted, reviewed, and finally approved — and what the system records about every step along the way.

Each box is one class, drawn in the standard three-part form: name, stereotype where it clarifies the role, and attributes with their types. Solid lines are associations, labelled with the verb that holds between the two classes and the multiplicity at each end; dashed lines mark a record that is copied or derived rather than linked by key.

The status a task moves through

One attribute carries the workflow: TaskAssignment.CompletionStatus. A check constraint limits it to five values, and every transition below is written by a stored procedure that re-checks the acting account’s role first.

Pending→ Acknowledged→ For Validation→ Completed · Needs Revision ↺ returns to the teacher, from For Validation or from Completed

Where the behaviour lives

The domain classes above are data holders. The rules of the system — who may create a task, who may approve it, what must be true before it completes — live in the application services and in four stored procedures that guard the same rules at the database.

Conventions used in the model

Two account classes, one role table

User and Teacher are stored separately so an assignment can only point at a teaching account, but both draw their permissions from the same Role table.

Polymorphic actors

AuthorType, ReaderType and RecipientType hold either User or Teacher. Because the reference can point at two tables, no foreign key is declared on those pairs.

Derived attributes

An attribute marked with a leading / is not stored. RoleName is read through a join on Role, so a role change takes effect everywhere at once.

Evidence is never overwritten

SubtaskProof holds the one current file per subtask; each submission is also copied into SubtaskProofHistory with an attempt number, so a returned attempt survives.

The inbox is a query, not a table

Notifications are assembled from assignments, proofs and comments when the page loads. Only read and hidden state is persisted, keyed by recipient and notification key.

Audit is append-only

TaskActivityLog records ten action types with the previous and new status, and a check constraint requires exactly one actor — a User or a Teacher, never both.
